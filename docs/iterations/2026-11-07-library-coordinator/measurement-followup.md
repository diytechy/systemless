# Measurement follow-up for release integration and ClockWerx pilot

Pending design; no new measurement is claimed here. Finish sequential source/native triage before implementing the final comparison instrumentation.

The current sampler's all-browser/Codex process boundary includes unrelated activity, and summed working sets can double-count shared pages. Keep those readings as context unless a narrower owned process boundary is independently established. Do not rename aggregate usage as game-only CPU or RAM. Current profiler JSON contains exported summary statistics rather than the sampled per-frame rows; add an explicitly versioned opt-in raw export if later analyses need those rows, retaining bulky raw data under D: and compact summaries in Git.

Investigate optional page memory measurement exposed through a local diagnostic button, feature-detected at runtime. The experimental measureUserAgentSpecificMemory API estimates application memory and can attribute dedicated workers; support/accounting is implementation-dependent. The [WICG draft](https://wicg.github.io/performance-measure-memory/) distinguishes dedicated-worker attribution from shared/service-worker measurements. Preserve any returned breakdown without assuming fixed keys/types.

The method needs a secure, cross-origin-isolated context and should be compared within the same browser version. These requirements and limits are described in the [MDN API reference](https://developer.mozilla.org/en-US/docs/Web/API/Performance/measureUserAgentSpecificMemory). If unavailable, record that result; the older performance.memory JS-heap estimate is not an equivalent total-memory fallback. [Google's implementation guidance](https://web.dev/articles/monitor-total-page-memory-usage) explains GC-dependent resolution and incomplete accounting. Schedule repeated memory samples outside timed frame captures to avoid contaminating frame-work measurements, and record capture age/scene. A returned page estimate is not unique physical RAM or GPU memory, and does not isolate emulation overhead.

Expose diagnostics as ordinary local app UI and exported JSON, then use supported IAB controls/DOM reads. Do not use hidden runtime inspection or raw debugging transports. Keep browser/environment configuration unchanged during the three-way comparison. The user already cleared the previous Edge game-tab activity concern; close each new test route before another emulator/build/conversion begins.

Responsiveness needs a defined boundary. Runtime execution/round-trip p95 and animation callbacks are useful work/scheduling measures; neither is input-to-displayed-response latency. If a reliable common event-to-visible-change method is unavailable, report observed action responsiveness and explicitly leave physical/display latency unmeasured. Startup, warm/cold cache state, bundle/media bytes, sound state, logical/output size, scene progression and game-time pace must accompany the final repeated comparisons.
